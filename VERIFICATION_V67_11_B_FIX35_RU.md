# Проверка ToyOS v67.11-B FIX35 — Ring3 Exception Containment

## 0. Цель

FIX35 считается успешным только если ошибка Ring3 EXE1 завершает именно виновный PID, а shell и остальные RT/MT задачи продолжают работать без перезагрузки. Проверяются #UD=6, #GP=13, #PF=14. FIX34A остается точкой отката до полного прохождения тестов.

## 1. Базовая загрузка

Собрать штатным `build.sh` в W64DevKit, загрузить образ в QEMU. Выполнить `ls`. В корне должны присутствовать `FAULTUD.EXE`, `FAULTGP.EXE`, `FAULTPF.EXE`, `PROCID.EXE`.

До fault-тестов проверить `ps`, `mtstat`, `rtstat`. Команды должны работать как в FIX34A.

## 2. Foreground #UD — обязательный первый тест

Выполнить:

    exec FAULTUD.EXE

Ожидается одна диагностическая строка ядра вида `PROCESS FAULT PID=N TYPE=FG VECTOR=6 EIP=...`, затем возврат к `toy0>` без зависания. Немедленно ввести:

    ps

Запись `FAULTUD.EXE` должна быть `FG EXITED ... FAULT`. Запомнить PID=N и выполнить:

    ps N

Ожидается: TYPE=FG, STATE=EXITED, EXIT=FAULT, VECTOR=6, EIP ненулевой, CR2=0. Затем выполнить `ls`, `ps`, `mtstat`, `rtstat` — shell должен оставаться интерактивным.

## 3. Foreground #GP и #PF

Последовательно:

    exec FAULTGP.EXE
    ps
    ps <PID_FAULTGP>

Ожидается VECTOR=13, EXIT=FAULT, система продолжает работать.

Затем:

    exec FAULTPF.EXE
    ps
    ps <PID_FAULTPF>

Ожидается VECTOR=14, EXIT=FAULT, CR2 соответствует тестовому адресу 0x50000000 (в `ps PID` значение сейчас выводится десятичным: 1342177280). Система продолжает принимать команды.

## 4. MT containment — сначала одна fault-задача рядом с нормальными MT

Запустить несколько штатных минимальных MT и одну fault-задачу, например через обычный синтаксис `execmt` вашего набора:

    execmt MT01.EXE MT02.EXE FAULTUD.EXE MT03.EXE

Подождать 1–2 секунды. Выполнить:

    ps
    mtstat

FAULTUD должна перейти в `MT EXITED ... FAULT`. Остальные MT должны остаться READY/RUNNING, а их D/Q/C в `mtstat` должны продолжать увеличиваться. Найти PID fault-задачи и выполнить `ps PID`: VECTOR=6, TYPE=MT, EXIT=FAULT.

Повторить отдельными загрузками для `FAULTGP.EXE` и `FAULTPF.EXE`. После каждого fault `mtstat` оставшихся MT должен продолжать расти. Завершить `mtstop all`; команда должна отработать с первого Enter, как в FIX28/FIX34A.

## 5. RT containment

Запустить FAULTUD как RT через штатный RTD/F10 механизм с параметрами:

    FAULTUD.EXE 10 10 1

После сообщения о старте и возврата `toy0>` система НЕ должна зависнуть. Для background RT fault не должно быть асинхронной строки `PROCESS FAULT` в общей консоли. Выполнить:

    ps

Соответствующий RT PID должен быть `EXITED ... FAULT`. Затем `ps PID`: TYPE=RT, EXIT=FAULT, VECTOR=6. `rtstat` и обычный ввод команд должны работать.

Повторить для FAULTGP и FAULTPF. Для #PF проверить VECTOR=14 и CR2=1342177280.

## 6. RT fault при работающих нормальных RT

Запустить 2–4 обычных SENSOR и дополнительно fault RT (не превышая 8 слотов). После fault выполнить дважды с интервалом несколько секунд:

    rtstat
    ps

Fault PID должен быть EXITED/FAULT. Jobs нормальных SENSOR должны продолжать увеличиваться. Остановка `RTSTAT STOP SLOTn` для живых SENSOR должна работать штатно. Fault одного RT не должен останавливать остальные RT.

## 7. Совместная нагрузка MT + RT

Запустить несколько обычных MT и несколько SENSOR RT. Убедиться по `mtstat`/`rtstat`, что обе группы работают. Затем добавить fault только в одну из групп (если нужен новый EXECMT-сеанс — сначала штатно завершить предыдущий).

После fault проверить:

    ps
    mtstat
    rtstat

Только виновный PID должен быть EXITED/FAULT. Счетчики оставшихся задач должны продолжать изменяться.

## 8. Регрессия FIX34A identity

При активных MT и RT выполнить:

    exec PROCID.EXE

PROCID должен по-прежнему сообщать TYPE:FG. Затем запустить PROCID как MT и RT и проверить его данные через MTDATA/RTDATA по методике FIX34A. Новый containment не должен менять определение текущего владельца Ring3-контекста.

## 9. Регрессия VGA FIX32

При активных фоновых задачах:

    exec VGADRV.EXE SPLASH.RAW

Изображение должно оставаться до реального нажатия клавиши, затем должен корректно восстановиться текстовый режим и shell. `VRAM map failed` недопустим.

## 10. WATCH/ESC и консоль

Проверить `rtstat watch`, ESC; затем `mtstat watch`, ESC. После выхода ввести несколько обычных команд. Курсор, prompt и ввод не должны зависать. Повторить после хотя бы одного contained RT fault.

## 11. Повторное использование PID/слота

После fault запомнить PID и слот. Запустить новую задачу, которая занимает тот же MT/RT slot. Новый экземпляр обязан получить новый PID. Старый PID через `ps <старый PID>` может исчезнуть после переиспользования слота — FIX35 не вводит историю процессов; это нормально. Текущий PID не должен наследовать FAULT metadata предыдущего экземпляра.

## 12. Что считается провалом

Провал: QEMU/ToyOS зависает; после fault нельзя вводить команды; fault одной RT/MT останавливает другие задачи; background fault печатает в общей консоли; PID/TYPE/SLOT не соответствуют реальному виновнику; новая задача наследует старый FAULT; #UD/#GP/#PF из Ring3 попадает в старый бесконечный fatal halt; ломается VGADRV, WATCH/ESC или `mtstop all`.

## 13. Ограничение FIX35

FIX35 намеренно содержит только #UD/#GP/#PF Ring3 EXE1. Ring0 exception остается fatal. Другие exception vectors пока остаются на старом fatal path. Нет wait(), POSIX signals, parent/child, automatic restart или нового scheduler. Это будет рассматриваться отдельными этапами после runtime-подтверждения FIX35.
