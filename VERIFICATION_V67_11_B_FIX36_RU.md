# Проверка ToyOS v67.11-B FIX36

FIX36 основан строго на runtime-подтвержденном FIX35B. FIX34A не заменять и не удалять.

## 1. Сборка

Собрать штатным `build.sh` в W64DevKit тем же i686 toolchain, который использовался для стабильных версий. Проверить отсутствие новых warnings/errors и наличие EXIT0.EXE, EXIT7.EXE, PROCID.EXE, FAULTUD.EXE, FAULTGP.EXE, FAULTPF.EXE, SENSOR1..8 и MT01..25.

## 2. Нормальный foreground exit status

1. `exec EXIT0.EXE`
2. `ps` — записать PID EXIT0.
3. `wait PID` — ожидается `EXIT: NORMAL STATUS: 0`.
4. `exec EXIT7.EXE`, записать новый PID.
5. `wait PID` — ожидается `EXIT: NORMAL STATUS: 7`.
6. Повторный `wait` того же PID должен вернуть тот же результат, а не уничтожать его.

## 3. Fault result

Для FAULTUD/FAULTGP/FAULTPF по очереди выполнить `exec`, взять PID из `ps`, затем `wait PID`.
Ожидается EXIT=FAULT, STATUS=`-`; VECTOR соответственно 6/13/14. Для FAULTPF CR2 должен соответствовать 0x50000000 (1342177280). После каждого fault shell обязан принимать команды.

## 4. RT exit и повторное использование SLOT

Запустить EXIT7.EXE через RTD/F10 как RT-задачу. После её завершения выполнить `wait PID`: NORMAL/7. Затем занять тот же SLOT другой RT-задачей (новый PID). Снова выполнить `wait` старого PID: результат старого PID обязан сохраниться и не заменяться данными нового процесса.

Повторить с FAULTPF.EXE как RT-задачей при приоритете ниже всех SENSOR, между SENSOR и выше хотя бы одного SENSOR. Это обязательная регрессия FIX35B: никаких EXC/hang, старый shell context не повреждается.

## 5. MT exit и повторное использование MT slot

Запустить EXIT7.EXE в EXECMT вместе с обычными MT задачами. После завершения EXIT7 остальные MT должны продолжать увеличивать D/Q/C. `wait PID` завершившейся задачи: NORMAL/7. Завершить session `mtstop all` — с первого Enter. Создать новую session и проверить, что старый PID по-прежнему возвращает старый результат, пока он находится в 64-entry history.

## 6. Ожидание активного PID

Запустить фоновые RT/MT, выбрать реально активный PID и выполнить `wait PID`. Пока процесс активен, система не должна зависать или крутиться в busy-loop: RTSTAT/MTSTAT должны продолжать отражать работу после завершения ожидания. Для бесконечного SENSOR/MT сначала завершить процесс штатным способом из другого доступного сценария; если интерактивно завершить его во время синхронной команды нельзя, этот пункт проверять на конечной EXIT/FAULT задаче.

## 7. Совместная нагрузка

4 MT + 8 SENSOR RT, затем fault/exit тесты. Проверить `rtstat`, `mtstat`, `rtdata`, `mtdata`, `ps`, `wait`. RT jobs и MT D/Q/C должны продолжать расти согласно уже подтвержденной политике FIX35B.

## 8. Обязательные регрессии

- `rtstat watch`, ESC — выход с первого нажатия.
- `mtstat watch`, ESC — выход с первого нажатия.
- `mtstop all` — корректный возврат с первого Enter.
- PROCID.EXE: FG, MT и RT identity.
- `syscall-test` — обязательно останавливается для ввода `OK` и завершается успешно, также при RT и при RT+MT.
- `exec VGADRV.EXE SPLASH.RAW` — нормальный показ и возврат.
- ls/mkdir/read/write/cp/rm и обычный `exec HELLO.EXE`.
- 8 SENSOR: запуск F10, RTDATA SLOT1..SLOT8, RTSTAT; отсутствие фонового вывода SENSOR в общую консоль.

## 9. Граница истории

History ограничена 64 завершениями. После вытеснения старой записи `wait` старого неактивного PID должен сообщить `PID not found or result expired`, а не ждать бесконечно. Это штатное ограничение FIX36.

## Критерий приемки

FIX36 фиксировать как stable только после runtime-проверки W64DevKit/QEMU. Любой hang, EXC, потеря shell, остановка RT/MT статистики, неправильный status, потеря результата сразу после reuse slot или регрессия FIX35B означает отказ от фиксации и возврат к FIX35B.

## FIX36A: обязательная проверка сборки
Перед runtime-тестами убедиться, что W64DevKit полностью собирает `EXIT0.EXE` и `EXIT7.EXE` без `undefined reference to program_main`. Исправление касается только PE/COFF entry stub: `_start` переходит на `_program_main`, как в проверенных FAULT*.EXE. После успешной сборки выполнить все тесты FIX36 выше без сокращений.
