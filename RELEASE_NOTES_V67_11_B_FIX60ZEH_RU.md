# ToyOS v67.11-B FIX60ZEH — test harness source guard

## Цель

FIX60ZEH создан строго от подтверждённо стабильного FIX60ZEG. Главная цель — устранить ложные/неоднозначные FAIL `TESTMRT.TST`, не меняя scheduler, RT sweep, bounded MT slack, foreground ownership и рабочую логику SONAR.

## Причина строк 16–18

После FIX60ZEG `SYS_CONSOLE_READ` имеет два нормальных служебных возврата для интерактивного shell:

- `2` — shell действительно находится в idle и разрешено scheduler-окно background;
- `3` — одноразовый UI-event redraw после завершения detached MT/RT процесса, который писал в консоль.

`ASSERT CONSOLE_IDLE_TICKS` в FIX60ZEG принимал только код `2`. Поэтому законный одноразовый redraw `3` ошибочно завершал ASSERT с FAIL. Следующие `MT_PROGRESS` затем падали каскадно, потому что требуемое idle-окно не было создано полностью.

В FIX60ZEH код `3` поглощается как UI-event и не считается idle-тиком. ASSERT продолжает работу до истечения требуемого количества RT ticks. Любой другой возврат, включая ввод клавиши или ошибку, остаётся жёстким FAIL. Пороговые значения `MT_PROGRESS`, heartbeat и RT fairness не уменьшались.

## Уточнение по диагностике номера строки

После повторной проверки исходного скриншота установлено, что первоначально номер отказа был ошибочно прочитан как `48`; фактически на изображении указана строка `43`. Поэтому прежний вывод о «невозможном FAIL на RUN rtstat» не используется. Механизмы source guard, добавленные FIX60ZEH, остаются полезными как независимая проверка соответствия TST source, staged-копии и фактически интерпретируемого файла.

Для исключения неоднозначности сохранены два защитных механизма:

1. после копирования `TST/*.TST` и `TST/ACCEPT.TXT` в `build/TST` сборка делает `cmp` каждого staged-файла с исходником и немедленно останавливается при любом отличии;
2. если любой TST-файл завершается с FAIL, runtime test runner печатает фактический размер прочитанного файла и его FNV-1a 32-bit fingerprint. Это позволяет однозначно установить, какой именно файл интерпретировался с FAT-образа.

Для текущего `TST/TESTMRT.TST` FIX60ZEH ожидаются:

- bytes = `1685`;
- FNV-1a32 = `3848550741` (`0xE5643955`).

Если когда-либо снова появится невозможный номер строки, эти значения сразу покажут, совпадает ли runtime-файл с релизным исходником.

Дополнительно отказ `RUN ...` теперь печатает отдельное сообщение `TEST HARNESS FAIL ... RUN rejected`, а не только запись в финальном summary.

## Что не менялось

`src/kernel.c` полностью идентичен FIX60ZEG (SHA-256 `3af4e5b2a9c8610eaee3efb1b533836dadf843e1b212922c9fee354c860dd001`). Следовательно, не менялись:

- distinct-slot RT sweep;
- bounded MT slack;
- foreground ownership;
- RT/MT arbitration;
- `SYS_CONSOLE_READ` runtime-семантика и автоматический prompt redraw;
- `execmt SONARVWR.EXE` и SONARLOG resilience.

## TESTMRT

Сам тест остаётся обязательным acceptance-тестом. Строки 16–18 сохраняют исходные требования. Тест не удалён и его MT/RT пороги не ослаблены.
