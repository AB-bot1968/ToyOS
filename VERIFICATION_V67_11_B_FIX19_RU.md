# Проверка ToyOS v67.11-B FIX19

## Цель
Подтвердить расширение kernel area с 128 до 256 секторов без изменения FAT16 LBA 512 и без регрессии FIX18.

## 1. Сборка W64DevKit
Использовать тот же i686 W64DevKit, что и для предыдущих релизов. Выполнить `build.sh`. Ожидается строка вида `[KERNEL] kernel.bin: ... bytes (131/256 kernel-slot sectors)` (точное фактическое число может измениться при toolchain). Сборка не должна сообщать превышение 128 секторов. Лимит теперь 256.

Критерий PASS: build.sh завершается полностью, boot.bin = 512 байт, kernel.bin <= 131072 байт, все check-скрипты проходят.

## 2. Проверка bootloader
Bootloader обязан читать LBA 1..256 пятью DAP: 1,64,64,64,63 секторов. Получаемая область RAM непрерывна: 0x07E00..0x27DFF. Ни один запрос не пересекает 64-KiB границу. `check67.sh` проверяет эту карту автоматически.

Критерий PASS: `check67.sh` печатает PASS, система загружается до `toy0>` без disk fail.

## 3. Карта диска
Проверить:
- LBA 0 — boot sector;
- LBA 1..256 — kernel slot;
- LBA 257..511 — reserved gap (255 секторов);
- LBA 512 — FAT16 boot sector.

Критерий PASS: FAT16 по-прежнему монтируется как `FAT16 mounted at LBA 512`, `ls` показывает прежние файлы.

## 4. Проверка файловой системы
После загрузки выполнить `ls`, `ls BIN`, чтение существующего текстового файла, запуск `HELLO.EXE`. Затем создать/удалить тестовый файл штатными командами, если они использовались в предыдущем регрессионном тесте. Перезагрузить ОС и повторить `ls`.

Критерий PASS: данные FAT16 не повреждаются, запуск EXE работает после reboot.

## 5. Проверка безопасного scratch LBA
Запустить штатный `syscall-test`. Дисковая read/write/restore проверка теперь использует LBA 300. Это сектор reserved gap, а не kernel slot и не FAT16. После теста выполнить reboot.

Критерий PASS: syscall-test проходит; после reboot ядро загружается; FAT16 монтируется. Это особенно важно — использование старого LBA 65 после расширения запрещено, поскольку он теперь относится к kernel slot.

## 6. RT regression
Запустить F10 / четыре SENSOR согласно прежней процедуре. Проверить `rtstat`, `rtstat watch`, `rtstat dump`, `rtstat events`, `rtdata SLOT1` ... `SLOT4`. Наблюдать несколько минут.

Критерий PASS: фоновые SENSOR не пишут в общую консоль, статистика изменяется, RTDATA обновляется, нет самопроизвольного роста MISS/SKIP при штатной нагрузке.

## 7. FIX18 6-hour statistics regression
Повторить тесты из `VERIFICATION_V67_11_B_FIX18_RU.md`: ротация 5-минутных buckets, 6-часовое вытеснение, RESET, EVENTS, lifetime saturating MISS/SKIP и длительный soak.

Критерий PASS: поведение FIX18 не изменилось.

## 8. MT regression
Выполнить, например, `execmt MT01.EXE MT02.EXE MT04.EXE`, затем `mtlist`, `mtdata MT1`, `mtdata MT2`, `mtdata MT3`. Проверить отсутствие асинхронного вывода MT-задач. Завершить `mtstop all`.

Критерий PASS: MT переключаются по прежнему 20-ms quantum, MTDATA соответствует позиции в сессии, консоль не повреждается.

## 9. Совместный RT+MT тест
Оставить SENSOR1..SENSOR4 активными, запустить EXECMT. Одновременно наблюдать RTSTAT/RTDATA и MTLIST/MTDATA.

Критерий PASS: RT продолжает работать с прежним приоритетом, MT не разрушает RT slots, после `mtstop all` RT остаётся активным.

## 10. Длительный тест
Рекомендуется минимум несколько часов, затем 24 часа. Периодически проверять RTSTAT, EVENTS, RTDATA и FAT16. Выполнить несколько холодных перезапусков образа.

## Что проверено при подготовке исходников
В доступной Linux-среде `boot.S` собран GNU as/ld в PE/raw: boot.bin ровно 512 байт, сигнатура 55 AA. `check67.sh` подтверждает непрерывную 256-sector карту и отсутствие пересечения 64-KiB границ. Host regression `tools/test_rt_stats_window.c` проходит. Изменённые kernel/user-shell исходники проходят i386 freestanding compilation.

Полная штатная сборка и QEMU runtime здесь не заявляются как выполненные: окончательное подтверждение требуется вашим i686 W64DevKit и QEMU/целевой средой.
