# Циклическая очередь EXE1 — v23

## Назначение

v23 добавляет в Toy OS последовательный планировщик EXE1. Он запускает от 1 до
25 уже подготовленных файлов EXE1 из FAT16 по циклической очереди:

`FILE1 -> FILE2 -> ... -> FILEN -> FILE1 -> ...`

Каждый EXE1 занимает тот же единственный пользовательский слот `0x00100000`,
который используется обычной командой `exec`. Поэтому это не параллельное
исполнение: одновременно работает только один EXE1. Переход к следующему
элементу происходит после `SYS_EXIT` текущей программы.

## Команды shell

Обычный конечный режим:

`execq REPEAT FILE1 [FILE2 ... FILE25]`

где `REPEAT` находится в диапазоне `1..3000` и означает число полных проходов
очереди.

Пример:

`execq 10 HELLO.EXE TEST.EXE`

означает:

`HELLO -> TEST -> HELLO -> TEST ...`

до завершения 10 полных циклов.

Бесконечный режим:

`execq forever FILE1 [FILE2 ... FILE25]`

При этом `forever` задаёт число повторений `0` в ABI системного вызова.

### Остановка бесконечной очереди

Во время активной очереди shell синхронно ждёт завершения системного вызова,
поэтому обычную строку `execq-stop` в этот момент ввести в shell нельзя. Для
внешней остановки предусмотрена клавиша **Esc**: IRQ1 устанавливает флаг
остановки, и очередь завершается при ближайшем безопасном переходе EXE1 через
`SYS_EXIT`.

Есть также команда shell:

`execq-stop`

и системный вызов `SYS_QUEUE_STOP`. Команда shell полезна, когда очередь уже
завершилась/не активна, а `SYS_QUEUE_STOP` особенно важен для EXE1: вызов из
активного EXE1 немедленно завершает текущую очередь и возвращает управление
исходному shell.

Таким образом, EXE1 может самостоятельно принять решение о прекращении
бесконечной очереди.

## Системные вызовы

### SYS_EXEC_QUEUE = 15

ABI:

- `EBX` = адрес пользовательского массива имён;
- `ECX` = количество файлов, `1..25`;
- `EDX` = количество полных проходов, `1..3000`;
- `EDX=0` = бесконечный режим;
- `EAX` = `0` при нормальном завершении, `0xffffffff` при остановке/ошибке.

Для каждого элемента используется ровно 13 байт:

- 12 байт под имя FAT 8.3;
- 1 байт `NUL`.

То есть максимальный буфер для 25 файлов имеет размер `25*13 = 325` байт.
Shell передаёт именно такой массив.

Перед копированием kernel проверяет пользовательский диапазон целиком.
Имена затем копируются в kernel memory, поэтому исходный пользовательский
буфер может оставаться обычным стековым буфером shell/EXE.

### SYS_QUEUE_STOP = 16

`SYS_QUEUE_STOP` не имеет аргументов.

- из активного EXE1: устанавливает остановку и сразу завершает очередь;
- из shell при активной очереди: устанавливает флаг остановки;
- если очередь не активна: возвращает `0xffffffff`.

## Взаимодействие с SYS_EXEC/SYS_EXIT

Обычный `SYS_EXEC` сохраняет 19-словный IRET frame shell в
`saved_user_frame`.

Для очереди этот frame сохраняется **один раз**, при старте очереди. При каждом
`SYS_EXIT` kernel:

1. освобождает user-доступ к текущему image;
2. переходит к следующему имени в массиве;
3. после последнего файла возвращается к первому;
4. после достижения `REPEAT` восстанавливает исходный shell frame.

Поэтому после конечной очереди команда shell продолжает выполнение после
исходного `INT 80h SYS_EXEC_QUEUE`.

Если `SYS_EXEC_QUEUE` вызывается самим EXE1, существующий сохранённый shell
frame сохраняется, а текущий EXE заменяется первым элементом новой очереди.
Это позволяет строить EXE1-цепочки без прямого доступа к Ring-0.

## Требование к EXE1

Каждый файл должен быть подготовлен тем же `EXE1`-форматом, который уже
используется `mkexe`:

- заголовок 16 байт;
- magic `EXE1`;
- entry в допустимом диапазоне;
- image и BSS проходят обычные ограничения загрузчика;
- файл находится в FAT16 до запуска OS;
- программа должна завершаться через `SYS_EXIT`, если она должна передать
  управление следующему элементу очереди.

EXE1, который сам зациклился и никогда не вызывает `SYS_EXIT`, блокирует
последовательную очередь на этом элементе. Это намеренное свойство текущей
однопроцессной модели, а не скрытый таймерный preemption.

## Почему очередь последовательная

Текущая Ring-3 архитектура имеет один общий user image slot и один EXE stack.
Поэтому v23 не делает вид, что 25 EXE1 выполняются параллельно. Каждый элемент
полностью получает этот слот, работает и освобождает его через `SYS_EXIT`.

Это даёт детерминированный FIFO-порядок и сохраняет существующие ограничения
по памяти и размеру kernel image.

## Исправление v27: буфер имён только для чтения

`SYS_EXEC_QUEUE` не изменяет массив имён: kernel только читает его и немедленно
копирует имена в собственную таблицу очереди. Поэтому указатель `EBX` может
указывать не только на writable stack EXE/shell, но и на пользовательский
`.urodata`/read-only буфер. Проверяется `user_range`, а не `user_rw_range`.

Это важно для вызовов из EXE1, где список имён может быть статическим массивом
или таблицей строк. Формат ABI остаётся прежним: `count * 13` байт, максимум
25 элементов.

Также интеграционный тест `[15] SYS_EXEC_QUEUE x2` теперь передаёт настоящий
13-байтный packed slot `HELLO.EXE`, а не короткий C-string. Это исключает
ложное падение теста из-за неправильного тестового буфера.


## v29 — вложенные очереди

`execq` не меняет своего назначения: это последовательная циклическая очередь.
Новое правило касается только вызова `SYS_EXEC_QUEUE` из EXE1, который уже
является элементом активного `execq`. В этом случае текущая очередь становится
родительской, а переданный список — дочерней очередью.

Kernel сохраняет родительский список имён, индекс, номер завершённых кругов,
число повторений и режим `forever` в стеке глубиной до 4 уровней. После
завершения дочерней очереди текущий EXE выгружается, родительское состояние
восстанавливается и запускается следующий элемент родительской очереди.
Результат завершения дочерней очереди локален для неё и не подменяет результат
всей верхнеуровневой очереди.

Пример:

```text
execq 1 QPASS.EXE QNESTED.EXE QPASS.EXE
```

`QNESTED.EXE` запускает дочернюю очередь `QPASS.EXE -> QPORT.EXE`. Полный
порядок становится:

```text
QPASS(parent)
QNESTED(parent)
  QPASS(child)
  QPORT(child)
QPASS(parent)
```

После последнего `QPASS(parent)` shell получает управление как и раньше.
Если глубина вложенности превышает 4 уровня, `SYS_EXEC_QUEUE` возвращает
ошибку занятости и текущая родительская очередь продолжает работу.

Отдельный `exec QNESTED.EXE` без активного родителя также допустим: в этом
случае создаётся обычная верхнеуровневая очередь и после её завершения shell
восстанавливается.


## v30 — исправление запуска очереди из standalone EXE1

Исправлена ошибка v29 в `SYS_EXEC_QUEUE`: EXE1 мог быть источником очереди только
если уже находился внутри активного `execq`. Поэтому самостоятельный
`exec QNESTED.EXE` ошибочно получал `EXE_ERR_BUSY`.

Теперь `SYS_EXEC_QUEUE` из Ring 3 EXE1 разрешён в двух случаях:

1. EXE1 запущен shell напрямую — создаётся верхнеуровневая очередь, после её
   завершения восстанавливается shell frame.
2. EXE1 является элементом активного `execq` — сохраняется родительская очередь,
   запускается дочерняя очередь, а после её завершения родительская очередь
   продолжается со следующего элемента.

Это различие принципиально: только второй случай увеличивает `queue_depth`.
