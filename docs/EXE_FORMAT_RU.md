# EXE1: создание и выполнение исполняемых файлов в Toy OS v13

## 1. Зачем введён EXE1

В v13 исполняемый файл отделён от kernel.bin. Ядро остаётся одним raw-образом,
а пользовательская программа хранится в FAT16 как обычный файл `*.EXE`.

Чтобы не вводить ELF и relocation, используется минимальный собственный формат EXE1.
Он предназначен именно для учебного 32-битного ядра этого проекта.

## 2. Формат файла

Первые 16 байт имеют структуру little-endian:

| Смещение | Размер | Поле | Назначение |
|---:|---:|---|---|
| 0 | 4 | magic | `EXE1`, значение `0x31455845` |
| 4 | 4 | entry | абсолютный адрес точки входа |
| 8 | 4 | image_size | размер байтов, записанных после заголовка |
| 12 | 4 | bss_size | сколько байт обнулить после image |

После заголовка сразу располагается raw image программы.

В текущей реализации загрузочный адрес фиксирован:

```text
EXEC_LOAD_ADDR = 0x00100000
```

Поэтому пример `HELLO.EXE` имеет `entry = 0x00100000`.

## 3. Почему relocation не нужен

Программа компилируется и линкуется сразу на `0x00100000` — именно туда ядро
впоследствии копирует image. Все абсолютные адреса, сформированные linker'ом,
поэтому уже правильны. Таблица relocation не нужна.

Это сознательное ограничение учебной версии: программу нельзя произвольно
переместить в другую область без повторной линковки.

## 4. Исходный файл программы

`src/hello.c` — минимальная standalone Ring-3 программа. Она:

1. содержит собственный маленький wrapper `syscall3()`;
2. вызывает `INT 80h` для `SYS_CONSOLE_WRITE`;
3. выводит строку;
4. вызывает `SYS_EXIT`;
5. не использует libc, CRT или обычный hosted runtime.

Компиляция использует те же freestanding-ограничения, что и kernel:

- 32-bit i386;
- `-ffreestanding`;
- `-fno-pie`;
- `-fno-stack-protector`;
- `-fno-builtin`;
- отключение SSE/MMX/FPU;
- `-nostdinc -nostdlib`.

## 5. Компиляция и линковка

Сначала:

```text
gcc $CFLAGS -c src/hello.c -o build/hello.o
```

Затем `program.ld` задаёт начало image:

```text
. = 0x00100000;
```

И linker собирает text/data/rodata в один raw-compatible section:

```text
ld -m i386pe --image-base 0 -e _start -T program.ld -o build/hello.pe build/hello.o
```

Raw image извлекается:

```text
objcopy --only-section=.text -O binary build/hello.pe build/hello.raw
```

В `hello.raw` уже нет PE/COFF заголовков. Это именно байты, которые должны
оказаться в памяти начиная с `0x00100000`.

## 6. Создание EXE

Утилита `tools/mkexe.c` добавляет 16-байтовый заголовок:

```text
build/mkexe.exe build/hello.raw build/HELLO.EXE 0
```

Последний аргумент — размер BSS. В `HELLO.EXE` он равен нулю.

В общем случае формат позволяет иметь:

```text
[EXE1 header][image][zero-filled BSS]
```

Сам BSS в файл не записывается. Ядро обнуляет соответствующую область после
загрузки image.

## 7. Попадание EXE на FAT16

`tools/mkfat16.c` создаёт образ и помещает `HELLO.EXE` в корневой каталог.

В текущем образе:

- кластер 2 — `README.TXT`;
- кластер 3 и далее — `HELLO.EXE`;
- размер файла хранится в обычном FAT16 directory entry;
- цепочка кластеров записывается в обе копии FAT.

Поэтому при загрузке ОС kernel не знает, где физически находится `HELLO.EXE`:
он пользуется обычным FAT16 file API.

## 8. Команда shell

В v13 добавлена команда:

```text
exec FILE.EXE
```

Например:

```text
toy0> exec HELLO.EXE
```

Shell вызывает:

```text
sys_exec("HELLO.EXE")
```

а wrapper делает:

```text
INT 80h
```

с `EAX=SYS_EXEC` и указателем имени в `EBX`.

## 9. Работа SYS_EXEC внутри ядра

Dispatcher получает syscall в CPL0.

`exe_load()` выполняет следующие шаги:

1. проверяет, что другой EXE сейчас не выполняется;
2. открывает файл через существующий FAT16 API;
3. читает первые 16 байт заголовка;
4. проверяет magic `EXE1`;
5. проверяет `image_size`;
6. проверяет, что `entry` находится внутри image;
7. проверяет размер BSS;
8. читает image непосредственно по адресу `0x00100000`;
9. проверяет отсутствие лишних байтов после image;
10. обнуляет BSS;
11. отмечает страницы программы как user-accessible и writable;
12. сохраняет полный user IRET frame shell;
13. заменяет `EIP` на entry EXE;
14. заменяет сохранённый `ESP` на отдельный стек EXE;
15. оставляет `CS=0x1B` и `SS=0x23`;
16. обычный `iret` из ISR возвращает CPU уже в новую Ring-3 программу.

## 10. Почему используется отдельный стек

Shell использует страницу:

```text
0x003ff000..0x003fffff
```

EXE получает соседнюю страницу:

```text
0x003fe000..0x003fefff
```

с начальным:

```text
ESP = 0x003ff000
```

Это важно: программа не должна портить стек shell, потому что после `SYS_EXIT`
ядро должно вернуть shell прежний `ESP`.

## 11. Как программа возвращается в shell

В начале `SYS_EXEC` ядро сохраняет 19 слов текущего user frame.

Это включает архитектурные поля, которые реально присутствуют при переходе
CPL3 -> CPL0: регистры PUSHA, сегментные регистры, номер syscall, error word,
`EIP`, `CS`, `EFLAGS`, а для входа из CPL3 дополнительно следующие на стеке
`ESP` и `SS`.

`SYS_EXIT` вызывается программой через `INT 80h`.

Ядро:

1. выключает user-доступ к страницам EXE;
2. сбрасывает состояние `exe_active`;
3. восстанавливает сохранённые 19 слов;
4. выполняет обычный возврат из ISR.

В результате `iret` возвращает процессор прямо на инструкцию shell после
исходного `INT 80h SYS_EXEC`, то есть shell продолжает работать.

## 12. Защита границ

Для v13 введены следующие ограничения:

- image начинается только с `0x00100000`;
- максимальный размер image + BSS — `0x000e0000` байт;
- конец EXE не может выйти за `0x001e0000`;
- entry обязан находиться внутри image;
- пользовательские указатели проверяются через `user_range()`;
- writable user buffers дополнительно проверяются через `user_rw_range()`;
- одновременно запускается только один EXE;
- текущий EXE не может запустить второй EXE через тот же простой loader.

## 13. Почему вся область EXE RW

Это намеренное упрощение v13. Страницы EXE получают `PAGE_US | PAGE_RW`.
Поэтому code/data/rodata находятся в одной пользовательской области.

Это не современная W^X-модель. Для учебного первого загрузчика такая схема
намного проще. Разделение `.text` на read/execute и `.data` на read/write
можно добавить отдельной следующей версией после того, как базовый запуск
станет стабильным.

## 14. Полный путь от C-файла до CPU

```text
src/hello.c
    |
    | gcc -m32 / freestanding
    v
build/hello.o
    |
    | ld -T program.ld, address = 0x00100000
    v
build/hello.pe
    |
    | objcopy
    v
build/hello.raw
    |
    | mkexe
    v
build/HELLO.EXE
    |
    | mkfat16
    v
build/disk.img
    |
    | BIOS -> bootloader -> kernel
    v
FAT16 mounted
    |
    | toy0> exec HELLO.EXE
    | INT 80h
    v
kernel / exe_load()
    |
    | read FAT16
    | copy -> 0x00100000
    | map pages as user
    | set EIP = 0x00100000
    | set ESP = 0x003ff000
    v
iret
    |
    v
CPL3 HELLO.EXE
    |
    | INT 80h SYS_CONSOLE_WRITE
    | INT 80h SYS_EXIT
    v
kernel / exe_exit()
    |
    v
iret
    |
    v
CPL3 shell
```

## 15. Практическая последовательность проверки

После сборки ожидаются файлы:

```text
build/hello.o
build/hello.pe
build/hello.raw
build/HELLO.EXE
build/disk.img
```

В shell:

```text
toy0> exec HELLO.EXE
Hello from HELLO.EXE (Ring 3)
toy0>
```

Если файл отсутствует или заголовок неверный, `SYS_EXEC` возвращает ошибку,
а shell печатает `exec: FAIL` и продолжает работать.

## 16. Создание новой программы

Минимальный рабочий алгоритм для будущей программы:

1. создать `src/myprog.c`;
2. использовать только freestanding C и собственные syscall wrappers;
3. не использовать libc/CRT;
4. собрать теми же CFLAGS;
5. линковать через `program.ld` с адресом `0x00100000`;
6. извлечь raw image через `objcopy`;
7. определить размер BSS;
8. выполнить `mkexe RAW OUTPUT BSS_SIZE`;
9. поместить EXE в FAT16 image;
10. запустить `exec MYPROG.EXE`.

Это сознательно минимальный ABI: динамический линкер, shared libraries,
relocation, аргументы командной строки, heap и полноценная модель процессов
в v13 ещё отсутствуют.


## v14 — исправление EXE stack page

Исправлена ошибка page fault при запуске EXE. Начальный ESP программы равен `0x003FF000`; первая инструкция `call`/`push` записывает данные по адресу `0x003FEFFC`, то есть использует страницу `0x003FE000..0x003FEFFF`. В v13 эта страница имела запись PTE, но не имела `PAGE_US`, поэтому Ring 3 получал `#PF` с `ERR=7` (user write to a supervisor page). Теперь `paging_set_exec_user()` при запуске EXE явно устанавливает для `EXEC_STACK_PAGE` флаги `P|RW|US`, а при завершении снимает `US`. Добавлена отдельная регрессионная проверка этого условия.


## 17. v15 — диагностика и строгая проверка размера

v14 исправляла page fault стека EXE, но сообщение `exec: FAIL` было слишком общим:
все причины отказа возвращали одно и то же `-1`. В v15 загрузчик сохраняет отдельные
коды ошибок: `-3` — файл не найден/не удалось открыть, `-4` — короткий заголовок,
`-5` — неверный magic, `-6` — неверный размер image, `-7` — entry вне image,
`-8` — слишком большой BSS, `-9` — ошибка чтения image, `-10` — лишние байты в файле.
Shell теперь печатает код, например `exec: FAIL -3`.

Дополнительно размер файла проверяется непосредственно по FAT16 directory entry:
для корректного EXE должно выполняться строго `file_size = 16 + image_size`. Это
исключает неоднозначность между `image_size` и фактической длиной файла и позволяет
однозначно отличить обрезанный EXE от EXE с хвостом. После этой проверки чтение image
идёт с текущей позиции 16 байт непосредственно по адресу `0x00100000`.

Если после пересборки v15 команда всё ещё сообщает ошибку, код на экране однозначно
покажет этап отказа; это позволяет проверить именно содержимое FAT16-образа, а не
только наличие `build/HELLO.EXE` на Windows.
