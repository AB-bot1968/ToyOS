# ToyOS — обязательные правила разработки

**Документ является обязательным и постоянно обновляемым.**

Этот файл должен автоматически обновляться в каждом новом FIX/релизе, если изменилось правило разработки, тестирования, документирования, упаковки, Git-публикации, приёмки или базовый процесс выполнения задач. Изменение правила и его документирование выполняются в одном FIX. Язык документа — русский.

Ни один новый этап работы не должен начинаться без ознакомления с этим файлом, `TOYOS_CURRENT_STATE.md` и `TOYOS_ARCHITECTURE_VISION.md`.

## 1. Главный принцип

Основная цель — **постепенно развивать ToyOS, не теряя уже достигнутую стабильность**.

Из этого следуют четыре базовых требования:

1. известный рабочий код не изменяется без необходимости;
2. каждое изменение минимально по области и должно иметь проверяемую причину;
3. каждый шаг должен быть воспроизводимым, непротиворечивым и документированным;
4. работа над FIX доводится до законченного результата с полным исходным ZIP, а не останавливается на плане или незавершённом patch.

## 2. Обязательная пошаговая схема работы

Каждая задача реализуется последовательностью контролируемых шагов. Переход к следующему шагу разрешён только после фиксации результата предыдущего.

### Шаг 0. Зафиксировать исходную точку

Перед изменениями необходимо определить:

- точный baseline/ZIP;
- текущую версию;
- hashes критических файлов, если они важны для задачи;
- состав acceptance suite;
- подтверждённые работающие сценарии;
- область, которую задача **не должна** менять.

Если baseline не определён однозначно, код не изменяется до разрешения неоднозначности.

### Шаг 1. Воспроизвести или формализовать задачу

Для ошибки фиксируются:

- наблюдаемый симптом;
- команда/тест/сценарий;
- ожидаемое поведение;
- фактическое поведение;
- относящиеся строки FAIL/лога/скриншота.

Для новой функции фиксируются:

- входы/выходы;
- границы ответственности;
- требования совместимости;
- что считается успешным результатом.

Нельзя исправлять ошибку, которая ещё не локализована хотя бы до проверяемой гипотезы.

### Шаг 2. Провести системный анализ до изменения кода

Нужно проверить причинную цепочку, а не только ближайший симптом. Анализ должен определить:

- какие подсистемы реально участвуют;
- какие инварианты нельзя нарушать;
- возможные альтернативные причины;
- является ли FAIL ошибкой runtime, test harness, build/image pipeline или окружения;
- минимальную точку изменения.

Если данные противоречат гипотезе, гипотеза отбрасывается. Нельзя продолжать реализацию, игнорируя необъяснённое противоречие.

### Шаг 3. Сформулировать проверяемый план

План должен содержать:

- список изменяемых файлов;
- список файлов/подсистем, которые должны остаться неизменными;
- предполагаемый механизм исправления;
- тест/критерий каждого изменения;
- rollback point.

План не должен содержать скрытых «заодно» изменений.

### Шаг 4. Подготовить тестовый контракт

Перед или одновременно с кодом определяется, как доказать корректность.

Правила:

- существующий тест сначала анализируется, а не переписывается автоматически;
- тест нельзя ослаблять только для получения PASS;
- если тест неверен, это должно быть доказано архитектурным контрактом/runtime-наблюдением;
- новая runtime-функциональность получает автоматический TST, когда это технически возможно и осмысленно;
- документационная/host-инфраструктура проверяется host-checker, а не искусственным runtime TST;
- регрессии известных сценариев должны проверяться отдельно от новой функции.

### Шаг 5. Внести минимальное изменение

Изменяется только необходимый код.

Запрещено:

- массовое форматирование;
- переименование не относящихся сущностей;
- перестройка scheduler/ABI/FS «заодно»;
- удаление рабочих защитных проверок без доказанной причины;
- добавление generated `build/` в исходный архив.

Если возможно, критическая стабильная подсистема проверяется побайтным hash/diff относительно baseline.

### Шаг 6. Выполнить локальные проверки

Минимальный набор в зависимости от задачи:

- syntax/static checks;
- freestanding i386 compile соответствующих C/ASM модулей;
- host unit/integration tests;
- специальные checker scripts;
- проверка acceptance manifest/FAT payload;
- проверка отсутствия generated artifacts;
- полная target-сборка, если нужный W64DevKit доступен.

Нельзя писать «полная сборка PASS» или «QEMU PASS», если это фактически не выполнялось.

### Шаг 7. Выполнить runtime/acceptance-проверку

Когда изменение касается runtime, окончательная приёмка выполняется в целевой среде.

Если пользователь присылает runtime FAIL:

- сначала анализируется реальный номер строки/скриншот/лог;
- не допускается угадывание содержимого строки;
- перед изменением теста проверяется фактический файл и его соответствие образу;
- необъяснённый FAIL считается открытой проблемой и не маскируется.

### Шаг 8. Обновить обязательную документацию

До упаковки FIX обязательно проверить и при необходимости обновить:

- `TOYOS_ARCHITECTURE_VISION.md`;
- `TOYOS_CURRENT_STATE.md`;
- `TOYOS_DEVELOPMENT_RULES.md`;
- release notes;
- verification notes.

Если архитектура не менялась, в release/verification notes это указывается явно. Если текущее состояние изменилось, `TOYOS_CURRENT_STATE.md` обновляется обязательно.

### Шаг 9. Проверить непротиворечивость

Перед релизом необходимо сопоставить:

- код;
- тесты;
- документацию;
- VERSION;
- release notes;
- verification notes;
- Git/tag сведения.

Если два документа утверждают разные текущие правила, FIX не готов. Исторический документ может описывать старое состояние, но текущие три обязательных документа не должны противоречить друг другу.

### Шаг 10. Упаковать полный исходный релиз

Результат работы обязан включать:

- полный исходный tree;
- длинное понятное имя корневого каталога;
- отсутствие `build/` и временных файлов;
- ZIP;
- проверку `unzip -t` или эквивалент;
- контрольную SHA-256 ZIP;
- ссылку для скачивания.

Работа над FIX не считается завершённой без фактически созданного архива, если пользователь просил изменения исходников.

## 3. Правила изменения стабильного baseline

Стабильный baseline нельзя использовать как экспериментальную площадку без явного нового FIX.

Для каждого нового FIX:

- исходный stable ZIP сохраняется отдельно;
- новый каталог создаётся копированием baseline;
- изменения вносятся в новый каталог;
- старый frozen ZIP не перезаписывается;
- при неудачном эксперименте есть однозначная точка возврата.

Подтверждённый FIX60ZEI — текущая runtime-контрольная точка до появления нового runtime-релиза, прошедшего не меньшую приёмку.

## 4. Требования к исходному коду

- Код должен оставаться freestanding и совместимым с текущей i386/W64DevKit сборкой.
- Не вводить зависимости от host runtime/stdlib в Ring0/Ring3 код ToyOS.
- Не менять syscall ABI, layout, FAT или scheduler без необходимости задачи и отдельной проверки совместимости.
- Сохранять case-insensitive поведение команд/параметров там, где оно уже является контрактом.
- Комментарии к новым нетривиальным архитектурным решениям должны объяснять **почему**, а не повторять код.
- Не оставлять мёртвые экспериментальные ветви, временные debug hacks и generated binaries в source tree.
- Рабочий код не переписывать ради стиля.

## 5. Требования к тестовой системе

Действующий acceptance-контракт:

- bare `test` читает `TST/ACCEPT.TXT`;
- текущий стабильный набор — 45 тестов;
- все тесты выводят результат в консоль;
- `TST.LOG` запрещён;
- `B*.TST` запрещены;
- большой RAM report buffer запрещён;
- итог FAIL содержит имена тестов и номера строк;
- тесты и параметры должны сохранять регистронезависимость там, где это предусмотрено системой;
- тестовые файлы должны фактически попадать в FAT image и staged-копия не должна расходиться с source;
- runtime source fingerprint/диагностика используется, когда нужно исключить несовпадение TST в образе.

### Запрет «лечить тест» без причины

Нельзя:

- снижать threshold только потому, что тест упал;
- удалять тест только потому, что он мешает получить 45/45;
- заменять точную проверку на более слабую без архитектурного обоснования;
- считать тест ошибочным только потому, что runtime визуально выглядит нормально.

Можно изменять тест, когда доказано, что он требует поведения, запрещённого текущей production-архитектурой, как это было с foreground busy-wait против idle-shell MT contract. При этом исходный смысл/порог по возможности сохраняется.

## 6. Scheduler / RT / MT — особая зона стабильности

Scheduler меняется только при прямом доказательстве ошибки scheduler.

Перед любым изменением scheduler необходимо отдельно подтвердить, что проблема не является:

- test orchestration;
- console redraw;
- FAT/image mismatch;
- foreground ownership issue вне scheduler;
- внешним QEMU/host I/O;
- ошибкой конкретного Ring3 driver.

Текущие инварианты FIX60ZEF/ZEG/ZEI должны считаться защищёнными regression-контрактами.

## 7. SONAR и фоновые сервисы

- `SONARLOG.EXE` не должен останавливаться из-за viewer.
- `SONARVWR.EXE` для live use запускается `execmt`.
- viewer не должен превращаться в скрытый foreground→MT scheduler hack.
- cyclic log и Data Channel должны сохранять bounded поведение.
- изменения UART/Modbus/SONAR проверяются вместе с MT/RT/console regression, а не только изолированно.

## 8. Консоль и foreground

- Нельзя менять foreground continuation из случайного syscall/IRQ пути.
- Асинхронный background output и prompt redraw должны быть отделены от scheduler policy.
- После фонового вывода консоль должна оставаться интерактивной.
- Длительные проверки обязательно включают возврат к prompt и повторные команды (`rtstat`, `ps`, `mtstat` и т.п.).

## 9. Build и target validation

Основная целевая среда — x86 W64DevKit/i686 и QEMU.

Если локальная среда не соответствует target toolchain:

- выполняются все доступные source/static/host checks;
- ограничение явно фиксируется;
- итоговая target runtime-проверка остаётся пользователю;
- нельзя подменять её предположением.

После любого запуска build/helper необходимо удалить generated `build/` перед упаковкой source ZIP.

## 10. Документирование каждого шага

Для существенной задачи должно быть возможно восстановить ход решения по артефактам проекта.

Минимально фиксируется:

- исходный симптом/цель;
- установленная причина;
- изменённые файлы;
- неизменяемые защищённые части;
- выполненные проверки;
- ограничения проверки;
- runtime-результат пользователя, если он необходим;
- окончательное решение о фиксации версии.

Архитектурные причины идут в `TOYOS_ARCHITECTURE_VISION.md`; текущий статус — в `TOYOS_CURRENT_STATE.md`; постоянные правила — в `TOYOS_DEVELOPMENT_RULES.md`; конкретный FIX — в release/verification notes.

## 11. Правило остановки при противоречии

Если во время работы обнаружено одно из следующего:

- фактический номер FAIL не соответствует анализируемому;
- source и FAT image могут различаться;
- checker утверждает одно, runtime — другое;
- изменение требует нарушить защищённый инвариант без доказательства;
- два результата взаимоисключающие;

работа **не продолжается механически**. Сначала противоречие локализуется и документируется. Нельзя «идти дальше по плану», если база рассуждения стала недостоверной.

## 12. Прогресс выполнения задания

При длительной работе пользователь должен видеть ход выполнения, а не только итог.

Нужно сообщать существенные контрольные точки, например:

- baseline найден/сверён;
- причина установлена;
- минимальный diff внесён;
- compile/checkers проходят;
- acceptance/static audit завершён;
- ZIP сформирован и проверен.

Сообщения о прогрессе не заменяют фактический результат и не должны создавать впечатление, что build/runtime выполнен, если он не выполнялся.

## 13. Требования к release ZIP

Каждый изменённый исходный релиз:

- полный, а не patch-only;
- содержит исходники, TST, tools и документацию;
- не содержит `build/`;
- имеет проверяемое имя версии;
- проходит ZIP integrity check;
- получает SHA-256;
- предоставляется пользователю ссылкой для скачивания.
