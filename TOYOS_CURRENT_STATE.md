# ToyOS — текущее зафиксированное состояние проекта

**Документ является обязательным и постоянно обновляемым.**

Этот файл должен автоматически обновляться в каждом новом FIX/релизе, если изменилось хотя бы одно из следующего: текущая версия, стабильный baseline, состав acceptance-тестов, архитектурный инвариант, статус runtime-проверок, состав подсистем, текущая задача/ограничение, GitHub/tag/commit, правила сборки или известные риски. Обновление выполняется в том же изменении, которое меняет соответствующее состояние. Откладывать актуализацию на следующий FIX запрещено.

Язык документа — русский. Исторические сведения не должны подменять текущее состояние: устаревшее переносится в release/verification notes или историю, а здесь хранится именно действующий baseline и факты, подтверждённые на данный момент.

## 1. Назначение документа

`TOYOS_CURRENT_STATE.md` — краткая точка входа в проект для нового чата, разработчика или этапа работ. Перед любыми изменениями необходимо прочитать:

1. `TOYOS_CURRENT_STATE.md` — что сейчас считается рабочим и зафиксированным;
2. `TOYOS_DEVELOPMENT_RULES.md` — обязательные правила изменения проекта;
3. `TOYOS_ARCHITECTURE_VISION.md` — архитектура и причины принятых решений.

Эти три документа образуют обязательный актуальный контекст проекта и должны поддерживаться совместно.

## 2. Текущий FIX

Текущий исходный пакет: **ToyOS v67.11-B FIX60ZEJ**.

Назначение FIX60ZEJ — ввести постоянную проектную документацию состояния и правил разработки. Runtime ToyOS в FIX60ZEJ **не изменяется** относительно frozen FIX60ZEI.

FIX60ZEJ не является новым scheduler/runtime experiment. Он является документированным governance-слоем над подтверждённой стабильной системой.

## 4. Acceptance-система

Текущий `TST/ACCEPT.TXT` содержит **45 уникальных тестов**. Команда без параметров:

`test`

должна запускать полный список из `TST/ACCEPT.TXT`.

Действующий контракт тестовой подсистемы:

- результат выводится в консоль;
- `TST.LOG` не создаётся и не используется;
- большой RAM report buffer не используется;
- файлов `B*.TST` быть не должно;
- в конце выводится компактный итог и при FAIL — имена тестов и номера упавших строк;
- тесты не изменяются только ради получения PASS;
- изменение теста допустимо лишь после доказательства, что его старый контракт противоречит фактической архитектуре или проверяет неверное условие;
- новые runtime-возможности должны получать автоматические TST-проверки; если проверка относится к общей приёмке, тест включается в `ACCEPT.TXT`;
- документационные/host-tooling изменения не должны порождать бессмысленные runtime TST; для них применяются host-checkers.

Финальная runtime-приёмка стабильного FIX60ZEI: **45 PASSED / 0 FAILED**.

## 5. Scheduler, RT/MT и foreground — действующие инварианты

Действующий scheduler-путь восходит к FIX60ZEF/ZEG и считается стабильным.

Обязательные инварианты:

- foreground continuation имеет однозначного владельца;
- обычная foreground-команда после RT preemption продолжается с того же Ring3 frame;
- `SYS_CONSOLE_READ` не подменяет address space и не выполняет скрытое переключение foreground на MT;
- MT получает bounded slack только в разрешённых scheduler boundaries;
- RT имеет приоритет, но distinct-slot RT sweep не позволяет одному RT slot монополизировать burst;
- 4 RT 10/10 ms должны прогрессировать справедливо без искусственного систематического MISS/SKIP, созданного самим scheduler;
- исправление UI/test orchestration не является основанием менять стабильный scheduler без прямого runtime-доказательства ошибки;
- test harness обязан воспроизводить реальные scheduler boundaries, а не требовать фонового прогресса во время непрерывного foreground busy-wait.

Подробная история и обоснование находятся в `TOYOS_ARCHITECTURE_VISION.md`.

## 6. SONAR — текущее состояние

Текущий pipeline включает UART/Modbus/Data Channel и пользовательские сервисы SONAR.

Зафиксированные правила:

- `SONARLOG.EXE` является долговременным MT-сервисом и не должен прекращать работу из-за запуска viewer;
- live viewer запускается явно как MT-задача: `execmt SONARVWR.EXE`;
- viewer выводит bounded snapshot (8 последних записей), а не захватывает foreground надолго;
- `SONARLOG` и viewer используют согласованный циклический `/SONAR.LOG`;
- `TESTVWR.TST`, `TESTMRT.TST` и SONAR regression-набор защищают совместную работу viewer/logger/RT/MT/console.

## 7. UART / Modbus / Data Channel

В текущем baseline присутствуют:

- legacy polling `COMDRV.EXE` для COM1..COM4, 115200 8N1;
- `SYS_UART_TRANSPORT=70` — bounded IRQ-driven transport для COM1;
- `SYS_DATA_CHANNEL=71` — bounded Sensor/Data Channel;
- `src/modbus_rtu.c` — CRC16, Function 04, parse/timeout/retry foundation;
- SONAR использует этот стек как production-пример Ring3 sensor driver.

Потенциальное дальнейшее направление — Arduino через отдельный виртуальный/физический COM2 с сохранением SONAR на COM1. Это **ещё не реализованная функция** и не является частью FIX60ZEI/FIX60ZEJ.

## 8. Build и упаковка

Авторитетная полная сборка проекта выполняется в целевой среде x86 W64DevKit/i686. Если текущая среда не имеет требуемого toolchain, допускаются только доступные static/freestanding/host проверки; запрещено заявлять полный build/QEMU PASS без фактического выполнения.

Каждый исходный FIX, передаваемый пользователю, должен:

- содержать полный исходный код, а не patch-only набор;
- иметь длинное однозначное имя корневого каталога;
- не содержать сгенерированный `build/`;
- не содержать временные runtime-логи и мусор;
- проходить проверку целостности ZIP (`unzip -t` или эквивалент);
- предоставляться отдельным ZIP для скачивания;
- сопровождаться release/verification notes, если выполнялись изменения;
- сохранять известный рабочий код без не относящихся к задаче изменений.

## 10. Текущее правило изменения baseline

Любая новая разработка начинается от явно названного подтверждённого baseline. Перед первым изменением фиксируются:

- имя baseline;
- hashes критических файлов;
- список acceptance-тестов;
- известные работающие сценарии, которые запрещено сломать.

Если задача не требует изменения scheduler/kernel/runtime, эти части должны оставаться побайтно неизменными. Расширять область изменений «заодно» запрещено.

## 11. Текущие обязательные проектные документы

С этого FIX обязательными постоянно обновляемыми документами являются:

- `TOYOS_ARCHITECTURE_VISION.md` — архитектура, инварианты, причины решений;
- `TOYOS_CURRENT_STATE.md` — текущее подтверждённое состояние и baseline;
- `TOYOS_DEVELOPMENT_RULES.md` — процесс, требования, проверки и запреты.

Любой новый FIX обязан проверить, требуют ли изменения все три документа. Если состояние, архитектура или правила изменились — соответствующий файл обновляется **в том же FIX**. Нельзя завершать FIX с заведомо устаревшим проектным документом.
