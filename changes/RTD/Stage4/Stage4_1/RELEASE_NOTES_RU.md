# ToyOS v67 RTD — Stage 4.1: компаратор приоритета

## 1. База

Этап начат от зафиксированной рабочей версии:

- `ToyOS v67 RTD Stage3 F10 FIX1`.

Цель этапа — реализовать только чистую функцию сравнения RT-приоритетов и отдельный unit-test. Фактический выбор RT-задачи по приоритету на этом этапе **не включается**.

## 2. Изменение №1 — отдельный заголовок `src/rt_priority.h`

Добавлен общий для ядра и unit-test заголовок `src/rt_priority.h`.

Функция:

```c
rt_priority_compare(a, b)
```

имеет трёхзначный результат:

- `> 0` — `a` имеет более высокий приоритет, чем `b`;
- `0` — приоритеты равны;
- `< 0` — `a` имеет более низкий приоритет, чем `b`.

Правило Stage 4.1: **большее числовое значение `priority` означает более высокий RT-приоритет**.

Функция не изменяет аргументы и не имеет побочных эффектов.

## 3. Изменение №2 — подключение функции к `kernel.c`

`src/kernel.c` подключает `rt_priority.h`.

Это делает компаратор частью исходного кода ядра, но он пока не используется планировщиком.

## 4. Изменение №3 — scheduler behaviour preserved

`rt_pick_ready()` в Stage 4.1 не изменялся.

Следовательно, данная версия не меняет алгоритм выбора готовой RT-задачи. `period`, `deadline`, `SYS_RT_WAIT`, ESC, F10 и shell остаются на поведении Stage 3 F10 FIX1.

## 5. Изменение №4 — отдельный unit-test

Добавлен:

```text
tools/test_rt_priority.c
```

Тест использует **тот же `src/rt_priority.h`**, который подключается ядром. Проверяются:

- `0 == 0`;
- `1 > 0`;
- `255 > 1`;
- `0 < 1`;
- `1 < 255`;
- `127 == 127`.

## 6. Изменение №5 — regression test

Добавлен:

```text
check_rtd_stage4_1.sh
```

Тест проверяет существование компаратора, его форму, использование общего заголовка unit-test и отсутствие подключения компаратора к `rt_pick_ready()`.

## 7. Совместимость

Не изменялись:

- EXE1 ABI;
- обычный загрузчик EXE1;
- `SENSOR.EXE`;
- `SYS_RT_START=38`;
- `SYS_RT_INFO=39`;
- `SYS_RT_WAIT=40`;
- F10 queue/launch flow;
- ESC completion;
- сохранённый shell context;
- VGA/text transition;
- PIT 50 Hz;
- EXECMT.

## 8. Следующий этап

Stage 4.2 будет отдельно подключать `rt_priority_compare()` к алгоритму выбора готовой RT-задачи. До этого этапа priority arbitration намеренно не меняется.
