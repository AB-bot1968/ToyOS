# ToyOS v67 RTD Stage 3 FIX3 — исправление возврата RT-задачи в shell

## База

Рабочая исходная точка: `ToyOS v67 RTD Stage 3 FIX2`.

## Шаг 1. Причина неисправности

При `SYS_CONSOLE_READ` shell сохраняет Ring-3 контекст в `rt_shell_frame` перед передачей CPU RT-задаче. В Stage 3 при возврате RT→shell содержимое `EAX` сохранялось как значение, оставшееся от входа в syscall `SYS_CONSOLE_READ` (`2`). Shell использует специальное возвращаемое значение `2` только как внутренний сигнал «RT-квант завершён, продолжить ожидание клавиши».

Из-за смешения фаз shell мог преждевременно возвращаться из `readline()`, повторять приглашение или терять устойчивое состояние ввода. При быстром периоде это визуально проявлялось как непрерывный поток `SENSOR: tick` и невозможность нормально ввести следующую команду.

## Шаг 2. Изменение ядра

`rt_switch_to_shell()` теперь разрешает переключение только когда `rt_shell_waiting != 0`.

При обычном возврате RT-кванта перед восстановлением shell frame ядро явно устанавливает:

```c
rt_shell_frame[7] = 2u;
```

Значение `2` является внутренним сигналом только для продолжения ожидания ввода; `readline()` не печатает дополнительный prompt. После завершения **последней** RT-задачи используется отдельный результат `3`, и тогда prompt `toy0>` печатается один раз. После этого восстанавливается сохранённый shell CR3 и Ring-3 frame.

Это не меняет структуру существующего interrupt frame и не меняет ABI обычных EXE1.

## Шаг 3. Сохранённое поведение

Не изменялись:

- `ESC` и `SENSOR: ESC -> stopped`;
- возврат `toy0>` после завершения последней RT-задачи;
- `SYS_RT_WAIT`;
- периодический release/deadline accounting;
- PIT 50 Hz;
- существующий EXE1 loader;
- EXECMT scheduler;
- изолированные CR3/stack/image RT-задач.

## Шаг 4. Практический эффект

После запуска одной RT-задачи shell снова получает управление ввода после каждого RT-кванта и может принять следующую команду. Поэтому становится возможен сценарий запуска нескольких RT-задач без предварительного завершения первой.
