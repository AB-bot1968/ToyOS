# ToyOS v67 RTD — Stage 3: несколько одновременно работающих RT-задач

## 1. База

Stage 3 разработан непосредственно от зафиксированной рабочей версии
**ToyOS v67 RTD Stage 2 FIX2**.

FIX2 считается неизменяемой контрольной точкой. В Stage 3 не изменялись:

- механизм `ESC` и завершения `SENSOR.EXE`;
- восстановление приглашения `toy0>`;
- исправление `EXC 14`, связанное с сохранением Ring-3 shell frame;
- `SYS_RT_WAIT` как механизм окончания периодической job;
- существующий PIT 50 Hz;
- существующий EXE1 loader и формат EXE1;
- существующий EXECMT scheduler и его syscall ABI.

## 2. Цель Stage 3

В FIX2 одновременно существовала только одна detached RT-задача. Это не
позволяло проверить совместную работу нескольких независимых периодических
задач.

Stage 3 меняет только модель владения RT-слотами:

```text
FIX2:
    shell + RT0

Stage 3:
    shell + RT0 + RT1 + RT2 + RT3
```

Поддерживается до **4** одновременно активных detached RT-задач.

## 3. Изменение 1 — RT task pool

Добавлено:

```c
#define RT_MAX_TASKS 4u
```

В существующем `sched_tasks[]` используются первые четыре слота.
Каждый RT-слот сохраняет:

- собственный CR3;
- собственный image slot;
- собственный stack;
- собственный interrupt context;
- period/deadline/priority;
- состояние текущей job;
- счётчик deadline miss.

Новая отдельная таблица контекстов не вводилась.

## 4. Изменение 2 — подсчёт активных RT-задач

Добавлен:

```c
static volatile uint32_t rt_task_count;
```

Первая задача создаёт общий shell context FIX2.
Последующие задачи используют тот же сохранённый shell context и не
перезаписывают его.

При завершении одной RT-задачи `rt_task_count` уменьшается. Shell
восстанавливается только после завершения последней активной RT-задачи.

## 5. Изменение 3 — поиск текущей RT-задачи

Добавлен `rt_find_current()`.

Он определяет текущую RT-задачу по CR3 текущего Ring-3 контекста.
Это устраняет зависимость системных вызовов от одного глобального
`rt_task_id`.

Используется для:

- `SYS_RT_WAIT`;
- `SYS_RT_INFO`;
- `SYS_CONSOLE_POLL`;
- `SYS_EXIT`;
- `SYS_SCHED_EXIT`;
- запрета обычного `exec` из RT-задачи.

## 6. Изменение 4 — выбор готовой RT-задачи

Добавлен `rt_pick_ready()`.

Stage 3 намеренно выбирает готовую job по абсолютному deadline, а при
равном deadline — по номеру RT-слота.

Это сделано специально, чтобы не смешивать два изменения:

1. Stage 3 — несколько RT-задач;
2. следующий этап — arbitration по `priority`.

`priority` уже существует и учитывается в бюджетировании, как было введено
в Stage 2. Изменение порядка выбора по priority отложено до отдельного этапа.

## 7. Изменение 5 — одновременные release/deadline

Добавлен `rt_release_jobs()`.

Каждый PIT tick проверяет **все четыре RT-слота**.

Для каждой задачи независимо:

```text
next_release
      ↓
   job active
      ↓
   deadline
      ↓
 SYS_RT_WAIT
      ↓
 следующий release
```

Deadline miss одной задачи не меняет параметры другой.

## 8. Изменение 6 — запуск второй и последующих задач

`SYS_RT_START` больше не возвращает `EXE_ERR_BUSY` только потому, что уже
существует RT-задача.

RTD можно запускать повторно из shell:

```text
exec RTD.EXE SENSOR.EXE 20 20 3
exec RTD.EXE SENSOR.EXE 40 40 7
```

В результате существуют две независимые копии `SENSOR.EXE`, каждая в своём
CR3 и image slot.

Максимум:

```text
RT0 + RT1 + RT2 + RT3
```

Пятая попытка возвращает `EXE_ERR_BUSY`.

## 9. Изменение 7 — SYS_RT_WAIT

`SYS_RT_WAIT` теперь определяет вызывающую RT-задачу через `rt_find_current()`.

Контекст сохраняется в `sched_tasks[id].words`, после чего именно эта задача
переходит в `TASK_BLOCKED`.

Если готова другая RT-задача, CPU передаётся ей. Если готовых RT-задач нет,
восстанавливается shell.

## 10. Изменение 8 — ESC

`rt_stop_requested` теперь является bit mask:

```text
bit 0 → RT0
bit 1 → RT1
bit 2 → RT2
bit 3 → RT3
```

ESC относится к текущей RT-задаче.

Это сохраняет проверенный FIX2 принцип, но позволяет завершать задачи
независимо друг от друга.

После `SYS_EXIT` бит соответствующей задачи очищается.

## 11. Изменение 9 — память Ring-3

`user_range()` и `user_rw_range()` теперь распознают image всех активных RT
слотов, а не только одного `rt_task_id`.

При этом виртуальный адрес остаётся прежним: изолированность обеспечивается
разными CR3.

## 12. Изменение 10 — shell frame / EXC 14

Ключевой FIX2 invariant сохранён:

> IRQ0 никогда не записывает Ring-0 interrupt frame в `rt_shell_frame`.

Shell frame захватывается только при `SYS_CONSOLE_READ` из Ring 3.

Это изменение Stage 3 не отменяет и не ослабляет исправление FIX2.

## 13. Пользовательский интерфейс

Существующая команда остаётся:

```text
exec RTD.EXE SENSOR.EXE PERIOD_MS DEADLINE_MS PRIORITY [DELAY_MS]
```

Пример двух задач:

```text
exec RTD.EXE SENSOR.EXE 20 20 3
exec RTD.EXE SENSOR.EXE 40 40 7
```

Обе являются обычными EXE1-программами.

## 14. Что Stage 3 сознательно НЕ делает

Stage 3 не меняет:

- PIT 50 Hz;
- реальный 10-ms interrupt timebase;
- priority arbitration;
- новый EDF/fixed-priority scheduler;
- EXE1 ABI.

Это отдельные последующие этапы.

## 15. Контрольная точка

Если runtime-тест Stage 3 обнаружит проблему, откат выполняется непосредственно
к:

**ToyOS v67 RTD Stage 2 FIX2**.

Не требуется откатывать более ранние FIX1/FIX2 исправления shell/ESC.
