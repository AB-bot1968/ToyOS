# ToyOS v67 RTD — Stage 3 FIX2

## База изменения

Исходная версия: `ToyOS v67 RTD Stage 3 FIX1`.

Функциональная задача Stage 3 не изменяется: несколько независимых detached
RT-задач, каждая со своим CR3, образом, стеком и контекстом.

## Шаг 1. Наблюдаемая ошибка

Пользовательский runtime-тест:

    exec RTD.EXE SENSOR.EXE 20 20 3

в Stage 3 FIX1 приводил к зависанию системы уже при запуске первой RT-задачи.

## Шаг 2. Анализ причины

В обработчике IRQ0 Stage 3 после сохранения текущего RT-контекста задача
переводилась в `READY`. Далее `rt_pick_ready()` могла немедленно выбрать ту же
самую задачу.

При исчерпании `rt_runtime_budget` код не гарантировал возврат к shell, потому
что условие выбора разрешало повторно выбрать текущий активный job. Для
одно-задачной конфигурации это ломало базовый FIX2 сценарий: shell должен
получать управление после бюджетного кванта.

Таким образом, изменение Stage 3 превратило безопасный fallback FIX2
«RT -> shell» в потенциальный цикл «RT -> тот же RT».

## Шаг 3. Исправление планировщика

В `sched_irq_tick()` введён локальный признак `budget_hit`.

Алгоритм теперь такой:

1. Если текущая RT-задача выполняется, её Ring-3 frame сохраняется в её
   `sched_task.words`.
2. Состояние `RUNNING` переводится в `READY`.
3. Увеличивается `rt_runtime_ticks`.
4. При достижении `rt_runtime_budget` устанавливается `budget_hit` и runtime
   обнуляется.
5. При `budget_hit` сначала ищется **другая** готовая RT-задача.
6. Если другой RT-задачи нет, управление возвращается shell через уже
   проверенный `rt_shell_frame`.
7. Если budget ещё не исчерпан и готова другая RT-задача, происходит RT->RT
   переключение.
8. Если готова только текущая задача, её сохранённый контекст продолжается
   без ложного переключения через shell.

Это сохраняет поведение Stage 2 FIX2 для одной задачи и одновременно создаёт
безопасную основу для нескольких RT-задач.

## Шаг 4. Безопасное восстановление CR3 при ошибке загрузки

В `rt_start_task()` до вызова `execmt_load_one()` сохраняется `caller_cr3`.
Если загрузка RT-образа завершается ошибкой, ядро возвращается именно в CR3
вызвавшего контекста. Это исключает зависимость от текущего значения CR3 после
внутреннего переключения loader-а.

## Шаг 4. Контекстная безопасность

Новая логика не сохраняет kernel-mode frame в `rt_shell_frame`.

`rt_shell_frame` по-прежнему формируется только в `SYS_CONSOLE_READ`, когда
shell уже находится в Ring 3. Это сохраняет исправление, устранившее прежний
`EXC 14 / CS=8`.

## Шаг 5. Механизм нескольких задач

`rt_task_count`, `RT_MAX_TASKS=4`, per-task `rt_stop_requested`, индивидуальные
CR3/image/stack и выбор свободного слота по состояниям
`TASK_CREATE|TASK_STOPPED|TASK_EXIT` сохраняются без изменений.

## Шаг 6. Что намеренно не менялось

Не изменялись:

- ESC и `SENSOR: ESC -> stopped`;
- возврат `toy0>`;
- `SYS_RT_WAIT` и его сохранение контекста;
- 50 Hz PIT;
- ABI `RTD.EXE`;
- формат обычного `SENSOR.EXE` EXE1;
- существующий EXECMT;
- существующий обычный EXE1 loader.

Приоритет по-прежнему не является критерием выбора RT-задачи: настоящий
fixed-priority arbitration остаётся отдельным этапом.

## Шаг 7. Регрессионная инфраструктура

Добавлены:

- `check_rtd_stage3_fix2.sh`;
- этот файл документации;
- тест-план;
- verification-report;
- patch относительно Stage 3 FIX1.

`build.sh` теперь запускает `check_rtd_stage3_fix2.sh` после предыдущих RTD
проверок.

## Шаг 8. Документация изменений

Все существующие корневые `.md` сохранены для совместимости со старыми
регрессионными скриптами и дополнительно помещены в:

    changes/ProjectHistory/

RTD-история хранится в:

    changes/RTD/

Начиная с этого FIX новые RTD release/test/verification/patch-файлы размещаются
только в соответствующем каталоге `changes/RTD/...`.
