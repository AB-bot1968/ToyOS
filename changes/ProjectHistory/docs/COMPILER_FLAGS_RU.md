# Подробное объяснение параметров сборки W64DevKit

Проект собирается как freestanding 32-bit i386 ядро. Важно отличать компиляцию ядра от компиляции двух маленьких host-утилит, которые работают в Windows/Linux и создают/проверяют FAT16 image.

## Основная команда C-компиляции

`gcc $CFLAGS -c src/kernel.c -o build/kernel.o`

| Параметр | Назначение | Почему он выбран |
|---|---|---|
| `-Os` | Оптимизация размера | Ядро загружается фиксированным числом секторов; уменьшение бинарника оставляет запас и снижает требования к загрузчику. |
| `-ffreestanding` | Отключает предположение о hosted C environment | У Toy OS нет ОС, CRT и стандартной runtime-библиотеки. |
| `-fno-pie` | Не генерировать position-independent executable | Адреса ядра заранее известны: linker размещает его около `0x7E00`, а loader загружает туда же. |
| `-fno-stack-protector` | Убирает stack canary | В ядре нет runtime-функций поддержки canary; использование опции иначе приводит к unresolved symbols или зависимости от libc. |
| `-fno-asynchronous-unwind-tables` | Не создавать unwind metadata | Эти таблицы ядру не нужны и увеличивают raw image. |
| `-fno-unwind-tables` | Не создавать обычные unwind tables | По той же причине: нет исключений C++/unwinder. |
| `-fno-builtin` | Не считать функции вроде memcpy/memset обязательными встроенными libc | Все нужные примитивы памяти реализованы вручную. |
| `-nostdinc` | Не искать системные C-заголовки | Ядро само определяет `uint8_t/uint16_t/uint32_t` и не зависит от Windows headers. |
| `-nostdlib` | Не подключать стандартную библиотеку и CRT | Точка входа `_start` и весь runtime написаны в проекте. |
| `-Wall -Wextra -Werror` | Максимизировать диагностику и сделать предупреждения ошибками | Это учебный kernel: случайное неиспользуемое API или подозрительный код не должен проходить проверку. Эти флаги применяются отдельным строгим аудитом. |

## Ассемблер

`as --32`

`--32` заставляет GNU assembler генерировать 32-битный объект. Это обязательно для i386 protected mode и согласуется с x86 W64DevKit.

## Linker

`ld -m i386pe`

W64DevKit использует PE/COFF toolchain, а не ELF toolchain. `-m i386pe` явно выбирает 32-битный PE/COFF emulation.

`--image-base 0`

Запрещает linker выбирать обычный пользовательский PE image base. Для raw kernel это принципиально: VMA из linker script должны соответствовать физическим адресам, куда loader положил байты.

`-e _start`

Фиксирует `_start` как entry symbol. Kernel не должен зависеть от `_mainCRTStartup`, `main` или другого CRT entry point.

`-T liker.ld`

Используется именно требуемое имя linker script `liker.ld`. В нём задаётся адрес `0x7E00`, порядок секций, границы BSS и, в Ring-3 варианте, page-aligned user sections.

## objcopy

`objcopy -O binary ...`

Удаляет PE/COFF контейнер и оставляет raw bytes, которые BIOS loader читает с диска.

В Ring-0 варианте `.rdata` объединяется с `.text`, потому что raw extraction должен содержать строки и другие read-only константы вместе с кодом.

В Ring-3 варианте kernel `.rdata` переименовывается в `.krodata`, а user `.rdata` сохраняется отдельно как `.urodata`. Это необходимо, чтобы page tables могли выставить user-bit только на страницы shell.

## Host FAT16 tools

`gcc tools/mkfat16.c -O2 -s ...`

`-O2` ускоряет маленькую host-утилиту, `-s` удаляет символы из PE/EXE. Эти параметры применяются только к Windows/host utility, а не к ядру.

## Почему x86 W64DevKit

Для этого проекта нужен именно x86 вариант W64DevKit: target должен быть i686/i386. x64 compiler мог бы собирать host-программы, но не должен использоваться для 32-битного kernel ABI. Скрипт проверяет `gcc -dumpmachine` и останавливается при несовместимой архитектуре.

## Дополнительные Ring-3 механизмы

Ring-3 shell компилируется в отдельные `.utext` и `.urodata`. Linker выравнивает их по 4096 байт. Kernel создаёт identity page table для первых 4 MiB, но выставляет `PTE.U/S=1` только на shell code, shell rodata и одну user stack page `0x003FF000..0x003FFFFF`.

`CR3` получает адрес page directory, затем `CR0.PG` включается. Поэтому CPL3 shell действительно не может читать/писать supervisor-only kernel pages: при обращении к ним процессор создаёт page fault (#PF, vector 14).

`TSS.ESP0=0x001F0000` используется как kernel stack при privilege transition. User stack имеет другой адрес — `0x00400000` как верхняя граница страницы `0x003FF000`, поэтому он не пересекается с kernel image.


## Исправление EXC 13 / отсутствие ввода в Ring 3

В предыдущей сборке компилятор мог автоматически генерировать инструкции SSE/MMX (`MOVAPS`, `MOVDQA`, `XORPS` и другие) даже при freestanding-сборке. Для маленького учебного ядра это нежелательно: состояние FPU/SSE ещё не является частью механизма переключения контекста. Поэтому Ring-3 проект теперь явно запрещает автоматическую SIMD/FPU генерацию параметрами `-fno-tree-vectorize -fno-tree-slp-vectorize -mno-sse -mno-sse2 -mno-mmx -mno-80387`. Проверка `check3.sh` дополнительно запрещает появление таких инструкций в итоговом PE/COFF. Это устраняет скрытую зависимость пользовательского Shell от FPU/SSE и является обязательной частью проверки.

## Дополнительные флаги после исправления EXC 13

`-fno-tree-vectorize` и `-fno-tree-slp-vectorize` отключают автоматическую векторизацию циклов и выражений. Это важно для учебного ядра, где нельзя допускать скрытую генерацию SIMD-кода.

`-mno-sse`, `-mno-sse2`, `-mno-mmx`, `-mno-80387` запрещают генерацию соответствующих инструкций. Благодаря этому CPL0 и CPL3 Shell работают без необходимости предварительно включать и обслуживать FPU/SSE state.
