# ToyOS v67.11-B FIX24 — проверка запуска RT поверх MT

## Что исправлено
FIX24 устраняет зависание, воспроизведённое последовательностью: запустить 4 MT, подготовить 4 SENSOR через RTD, нажать F10. В FIX23 после первого успешного сообщения `RTD: started SENSOR1...` уже работающий 10-ms RT/MT scheduler мог переключить контекст внутри цепочки следующих короткоживущих RTD.EXE. Это делало foreground return-chain запуска нестабильным.

F10 теперь открывает короткую launch-critical секцию через внутреннюю операцию SYS_RT_STATS op=7. IRQ0 не запрещается: часы и RT release accounting продолжаются. На время пакетного запуска откладывается только dispatch RT/MT. После возврата всех RTD.EXE guard снимается, и обычный приоритет RT > MT восстанавливается. Нового syscall номера нет; ABI 0..54 не перенумерован.

## Обязательные тесты
1. Контроль: после загрузки выполнить обычные `ls`, `rtstat`, `mtstat`.
2. Главная регрессия: `execmt MT01.EXE MT02.EXE MT03.EXE MT04.EXE`, убедиться через `mtlist`, подготовить SENSOR1..SENSOR4 с period/deadline 10/10 и нажать F10. Должны появиться ровно четыре `RTD: started ...`; shell не должен зависнуть.
3. Сразу выполнить `rtstat`: активны SLOT1..SLOT4. Затем `mtstat`: MT-сессия остаётся активной.
4. Повторить порядок наоборот: сначала 4 RT, затем 4 MT.
5. Нагрузка: 4 MT + 8 RT. После F10 shell должен оставаться управляемым; проверить `rtstat watch`/ESC и `mtstat watch`/ESC.
6. Остановить RT по SLOT1..SLOT8. Убедиться, что MT DISPATCH/CPU_TICKS продолжают расти.
7. `mtstop all`, затем снова запустить 4 RT и проверить отсутствие регрессии RT-only.

## Что прислать при проблеме
Для каждого сценария: точную последовательность команд, последние 10 строк консоли перед зависанием, `rtstat`, `mtstat` (если shell доступен), и указать после какого именно `RTD: started` возникла проблема.
